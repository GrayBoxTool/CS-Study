## 1. 개요 및 정의
> 이 기술/개념이 무엇이고 왜 등장했는지 간략히 서술합니다.

- **개념 정의**:
  - **TLS 핸드셰이크**: 브라우저와 서버가 암호화 통신을 시작하기 전에 **"열쇠(세션 키)를 맞추고, 상대가 진짜인지 확인하는" 준비 절차**.
  - 주소창 자물쇠 🔒 뒤에서 벌어지는 일이 바로 이 과정이다.
- **등장 배경 및 해결하고자 한 문제**:
  - 그냥 HTTP는 **'엽서'**와 같다. 데이터는 공유기, 통신사 장비 등 여러 곳을 거쳐 가는데, 봉투 없이 보내면 거쳐 가는 누구나 다음을 할 수 있다.

| 위험 | 예시 |
| :--- | :--- |
| 엿보기 · 도청 | 카페 와이파이에서 누군가 내 비밀번호를 그대로 읽는다 |
| 바꿔치기 · 변조 | 송금할 계좌번호가 중간에서 다른 번호로 바뀌어 도착한다 |
| 사칭 · 위장 | 진짜 은행처럼 보이는 가짜 서버에 접속해 버린다 |

## 2. 핵심 동작 원리 및 특징
> 개념의 핵심 로직, 구조, 동작 흐름을 시각 자료나 표, 불릿 포인트로 정리합니다.

- **원리 1 – TLS가 지켜주는 세 가지**

| 막아야 할 위험 | TLS가 주는 것 | 어떻게? |
| :--- | :--- | :--- |
| 엿보기 · 도청 | **기밀성** | 내용을 암호화해서 읽을 수 없게 |
| 바꿔치기 · 변조 | **무결성** | 메시지마다 위조 방지 도장을 찍어서 |
| 사칭 · 위장 | **인증** | 인증서와 디지털 서명으로 신원 확인 |

  > 핸드셰이크는 이 세 가지를 위한 **'준비 절차'**다.

- **원리 2 – TLS의 위치: TCP 위, HTTP 아래**

```
HTTP  · 웹 페이지 내용
TLS   · 암호화 · 인증        ← HTTP + TLS = HTTPS
TCP   · 순서대로 빠짐없이
IP    · 주소 찾아가기
```
  1. TCP 3-way handshake로 연결
  2. TLS 핸드셰이크로 열쇠 맞추기
  3. 암호화된 HTTP 주고받기
  > HTTP 입장에선 평소처럼 말할 뿐, **포장은 TLS가 대신** 해준다.

- **원리 3 – 대칭키 vs 비대칭키, 그리고 핵심 아이디어**
  > **느리지만 안전한 방법(비대칭키)으로 열쇠만 정하고, 빠른 대칭키로 실제 대화를 한다.**  
  > 이 '열쇠를 정하는 과정'이 바로 TLS 핸드셰이크다.

- **원리 4 – 인증서는 서버의 '신분증'**

| 신분증 | 인증서 |
| :--- | :--- |
| 이름 | 도메인 (naver.com) |
| 사진 | 서버의 공개키 |
| 발급 기관의 직인 | CA(인증기관)의 서명 |
| 유효기간 | 유효기간 |

  - **믿음의 사슬(Chain of Trust)**: `루트 CA`(OS·브라우저에 미리 내장) → `중간 CA`(루트가 서명) → `naver.com`(중간 CA가 서명)

- **원리 5 – 전체 흐름: 왕복 한 번(1-RTT)이면 끝난다**
  0. (사전) TCP 3-way handshake 완료
  1. **① ClientHello** (브라우저 → 서버): 쓸 수 있는 암호 목록 · 랜덤값 · 내 키 재료(반쪽)
  2. **② ServerHello** (서버 → 브라우저): 고른 암호 · 랜덤값 · 서버 키 재료(반쪽)
     - 👉 **양쪽이 각자 같은 세션 키를 계산한다 (키 자체는 전송 안 됨)**
  3. **③ 인증서 · 서명 · Finished** (서버 → 브라우저): **여기부터 암호화되어 전송**
  4. **④ Finished** (브라우저 → 서버)
  5. **⑤ 암호화된 HTTP 데이터** 송수신

- **원리 6 – 열쇠를 보내지 않고 맞추는 법: 물감 섞기 (Diffie-Hellman 비유)**
  1. **공통 색(노랑)**은 모두에게 공개한다.
  2. 브라우저는 **비밀 빨강**, 서버는 **비밀 파랑**을 각자 고른다. (절대 안 보냄)
  3. 섞은 색만 교환한다. 브라우저 → **주황**, 서버 → **초록**  
     → 도청자는 섞인 색을 봐도 비밀 색을 분리해내기 어렵다.
  4. 브라우저: 받은 초록 + 내 빨강 = **갈색** / 서버: 받은 주황 + 내 파랑 = **갈색**  
     → **같은 갈색 = 세션 키** 🎨

- **비교 분석 표 – 대칭키 vs 비대칭키**:

| 구분 | 대칭키 | 비대칭키 (공개키 암호) |
| :--- | :--- | :--- |
| 방식 | 열쇠 하나로 잠그고, 같은 열쇠로 연다 | 열린 자물쇠(공개키)는 나눠주고, 여는 열쇠(개인키)는 나만 갖는다 |
| 장점 | 빠르다 | 열쇠를 건넬 필요가 없다 · 서명도 된다 |
| 단점 | 처음에 그 열쇠를 어떻게 건네지? | 느리다 |
| TLS에서의 역할 | 실제 HTTP 데이터 암호화 | 서버 인증(서명) · 키 합의 |

## 3. 실무 / 면접 핵심 포인트
> 면접관이 자주 묻는 꼬리 질문과 이에 대한 명쾌한 답변을 정리합니다.

### Q1. 왜 처음부터 끝까지 비대칭키로 암호화하지 않을까?
- **A**: 비대칭키 연산은 대칭키보다 훨씬 느리기 때문입니다. 대신 대칭키는 "처음에 열쇠를 어떻게 안전하게 건네느냐"는 문제가 있습니다. 그래서 TLS는 두 방식을 섞어 씁니다. 핸드셰이크에서는 비대칭키 기술로 **서버를 인증하고 세션 키를 합의**하고, 이후 실제 데이터는 **빠른 대칭키**로 암호화합니다.

### Q2. 세션 키는 네트워크로 전송될까?
- **A**: 전송되지 않습니다. ClientHello와 ServerHello에서 각자의 **키 재료(반쪽)**만 주고받고, 양쪽이 자신의 비밀값과 상대의 키 재료를 조합해 **각자 같은 세션 키를 계산**합니다(Diffie-Hellman, '물감 섞기' 원리). 도청자는 오가는 키 재료를 봐도 비밀값을 분리해낼 수 없어서 세션 키를 알 수 없습니다.

### Q3. 인증서 확인을 건너뛰면 어떤 공격이 가능할까?
- **A**: **중간자 공격(MITM, Man-In-The-Middle)**이 가능해집니다. 공격자가 중간에서 서버인 척 자기 키 재료를 보내면, 브라우저는 진짜 서버가 아닌 공격자와 세션 키를 맞추게 됩니다. 암호화는 되어 있어도 그 상대가 공격자이므로 내용이 모두 노출되고 변조될 수 있습니다. 그래서 인증서의 **CA 서명, 도메인, 유효기간, 신뢰 체인**을 검증하는 단계가 반드시 필요합니다.
