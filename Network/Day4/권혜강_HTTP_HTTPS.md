## 1. 개요 및 정의
> 이 기술/개념이 무엇이고 왜 등장했는지 간략히 서술합니다.

- **개념 정의**:
  - **HTTP**: 브라우저가 요청(Request)을 보내고 서버가 응답(Response)을 돌려주는 웹 통신 규칙.
  - **HTTPS**: HTTP 통신에 **TLS 보안 계층**을 더한 것. → **HTTP + TLS = HTTPS**
- **등장 배경 및 해결하고자 한 문제**:
  - HTTP만 쓰면 요청과 응답이 **평문**으로 오가기 때문에, 전송 중에 누군가 내용을 **읽거나(도청) 바꿀 수(변조)** 있다.
  - 예: `POST /login password=cherry123` 같은 로그인 요청이 네트워크에서 그대로 보임.
  - HTTPS는 이 데이터가 **이동하는 구간**을 보호하기 위해 등장했다.

## 2. 핵심 동작 원리 및 특징
> 개념의 핵심 로직, 구조, 동작 흐름을 시각 자료나 표, 불릿 포인트로 정리합니다.

- **원리 1 – HTTPS가 지키는 세 가지**

| 보안 요소 | 의미 | 키워드 |
| :--- | :--- | :--- |
| 기밀성 | 내용을 암호화해 중간에서 읽기 어렵게 함 | 암호화 |
| 무결성 | 전송 중 데이터가 바뀌었는지 확인 | 변조 감지 |
| 서버 인증 | 인증서로 접속한 도메인의 서버가 맞는지 확인 | 신원 확인 |

  > 인증서는 **도메인과 신뢰 체인**을 확인하는 단서일 뿐, 사이트의 사업 내용까지 보증하지는 않는다.

- **원리 2 – HTTPS 보안이 시작되는 순서**
  1. **주소 접속**: `https://` 사이트에 연결 요청
  2. **서버 인증**: 인증서 · 도메인 · 서명 검증
  3. **키 합의**: 임시 키 교환으로 공유 비밀 생성
  4. **암호화 통신**: 양쪽이 만든 키(대칭키)로 요청·응답 보호

  > 공개키로 본문 전체를 암호화하지 않는다. 먼저 안전하게 쓸 **대칭키를 함께 만든다.**

- **원리 3 – 공개키 암호화의 기본 원리**
  - 수신자의 **공개키로 암호화**한 데이터는 짝이 되는 **개인키로만 복호화**할 수 있다.
  - 단, **TLS 1.3은 이 방식으로 세션키를 보내지 않고**, 아래처럼 키를 **합의**한다.

- **원리 4 – TLS 1.3의 키 합의 흐름**
  1. **ClientHello**: 지원 방식 + 브라우저의 임시 공개 키
  2. **ServerHello**: 선택한 방식 + 서버의 임시 공개 키
     - 브라우저: `내 개인 키 + 서버 공개 키` → 공유 비밀 계산
     - 서버: `내 개인 키 + 브라우저 공개 키` → **같은** 공유 비밀 계산
  3. **서버 인증서 + 서명 + Finished**: 브라우저가 도메인 · 신뢰 체인 · 서명 확인
  4. **Client Finished** 확인 → 이후 **암호화된 HTTP** 송수신
  > 임시 공개 키는 오가지만, **비밀키나 세션키 자체는 네트워크로 보내지 않는다.** 양쪽이 계산한 비밀에서 대칭키를 파생한다.

- **원리 5 – HTTPS가 보호하는 범위**

| 보호하는 것 | 대신 조심할 것 |
| :--- | :--- |
| ✓ 전송 중 데이터 도청 | 피싱 사이트도 HTTPS를 쓸 수 있음 |
| ✓ 전송 중 데이터 변조 | 내 기기나 서버가 해킹되면 별도 위험 |
| ✓ 접속 서버의 인증서 확인 | 자물쇠가 사업자 신뢰성을 보증하지 않음 |

  > HTTPS는 **안전한 통신 통로**를 만들 뿐, 통로 양 끝(기기·서버)의 안전까지 보장하지는 않는다.

- **비교 분석 표**:

| 구분 | HTTP | HTTPS |
| :--- | :--- | :--- |
| 기본 동작 | HTTP 요청·응답 | HTTP + TLS |
| 전송 내용 | 평문 전송 | 암호화된 전송 |
| 서버 확인 | 기본 제공 안 함 | 인증서로 도메인 확인 |
| 변조 확인 | 기본 제공 안 함 | 무결성 검증 |
| 기본 포트 | 80 | 443 |
| 장점 | 구조가 단순하고 핸드셰이크 오버헤드가 없음 | 기밀성 · 무결성 · 서버 인증 제공 |
| 단점 | 도청 · 변조 · 사칭에 취약 | 연결 시 TLS 핸드셰이크 과정이 추가됨 |

  > 포트는 기본값일 뿐이다. HTTP/3은 TCP 대신 QUIC을 사용하지만, HTTPS의 핵심은 여전히 TLS 보안이다.

## 3. 실무 / 면접 핵심 포인트
> 면접관이 자주 묻는 꼬리 질문과 이에 대한 명쾌한 답변을 정리합니다.

### Q1. HTTP와 HTTPS의 차이를 설명해 주세요.
- **A**: HTTP는 요청과 응답을 평문으로 주고받는 프로토콜이라 전송 중 도청이나 변조에 취약합니다. HTTPS는 HTTP에 TLS 계층을 더해 **기밀성(암호화), 무결성(변조 감지), 서버 인증(인증서)**을 제공합니다. 기본 포트는 HTTP가 80, HTTPS가 443입니다.

### Q2. HTTPS는 데이터를 공개키로 암호화하나요?
- **A**: 아닙니다. 본문 전체를 공개키로 암호화하지 않습니다. TLS 핸드셰이크에서 먼저 양쪽이 같은 대칭키를 만들고, 실제 요청·응답은 **빠른 대칭키 암호화**로 보호합니다. 특히 TLS 1.3은 임시 공개 키를 교환해 각자 같은 공유 비밀을 계산하므로, **세션키 자체가 네트워크로 전송되지 않습니다.**

### Q3. HTTPS를 쓰는 사이트는 무조건 안전한가요?
- **A**: 아닙니다. HTTPS는 브라우저와 서버 사이 **전송 구간**을 보호할 뿐입니다. 피싱 사이트도 인증서를 발급받아 HTTPS를 쓸 수 있고, 자물쇠 표시는 사업자의 신뢰성을 보증하지 않습니다. 또한 기기나 서버 자체가 해킹된 경우는 별도의 보안 문제입니다.
